# Budget: аудит выпуска и UX/UI

Дата: 17.11.2026. Проверена текущая рабочая копия, облачная `/` и локальная `/free/`.
Аудит без исправления приложения, публикации и изменения рабочих данных.

**Вердикт: широкий production-выпуск преждевременен.** В облачной версии обнаружены ошибки, способные изменить другой период, частично выполнить финансовую операцию и потерять параллельные правки. В локальной версии есть потеря параллельных правок и риск перезаписи автокопии старым состоянием. Для публичного облака с независимыми пользователями дополнительно блокирует выпуск текущая модель доступа.

| Вариант выпуска | Решение |
|---|---|
| Существующий семейный бюджет | До расширения использования исправить гонки периода и составные операции; текущие суммы сами по себе этим аудитом не проверены |
| Бесплатный публичный `/free/` | Сначала исправить целостность данных и период, затем ограниченный пилот и реальные телефоны |
| Облако для разных семей | Не выпускать до изоляции бюджетов, воспроизводимой схемы и проверок прав |
| Платный продукт | Готовность не подтверждена: сначала надёжность и пилот; модель оплаты, поддержки и условия сервиса требуют отдельного решения |

Приоритеты: P0 = блокер соответствующей модели выпуска; P1 = исправить до широкого релиза; P2 = существенное улучшение следующего этапа; P3 = полировка. Это приоритеты продукта, не классификация доказанной эксплуатации уязвимостей.

## Production: подтверждённые дефекты

### D01 · P0 для публичного облака · Все авторизованные работают с общими данными

`supabase_setup.sql:14–27`: политики `authenticated using (true) with check (true)` разрешают доступ ко всем строкам трёх таблиц. Для закрытого общего семейного бюджета это заданная модель; для независимых пользователей она непригодна. Фактические политики и возможность регистрации в production не проверены: утверждения об утечке нет.

Исправление: бюджет/членство в схеме, RLS по членству, проверка связей при записи. Готовность: пользователь A не читает и не меняет бюджет B прямым API, через подмену FK и Realtime.

### D02 · P1 · Покрытие перерасхода списывает накопления другого периода

`app.js:459–464`: `coverFrom()` сначала ждёт сохранения строки, после чего читает изменяемые `state.monthId/state.saved`. Если за это время сменить период, следующий запрос уменьшит накопления нового периода. В локальном VM-воспроизведении обновился план `old-entry`, затем `saved` у `new-month`.

Исправление: фиксировать контекст операции до первого `await`; выполнять изменение плана и источника транзакционно. Готовность: задержать первый запрос, переключить период, завершить запрос; новый период неизменен.

### D03 · P1 · Ответ сохранения подменяет строку нового периода

`app.js:248–254,342–367`: `setPaid()` и `saveEntry()` запоминают индекс до запроса и пишут по нему после `await`. К этому моменту `state.entries` может принадлежать другому периоду. VM подтвердил замену новой строки старой. Следующая правка такой строки обращается к ID старого периода.

Исправление: проверять ID периода, находить строку по ID после ответа, не вставлять ответ в чужой экран. Проверить также остальные асинхронные обработчики добавления и переноса. Готовность: искусственная задержка, смена периода, ответ; состав строк текущего периода остаётся правильным.

### D04 · P1 · Финансовые операции выполняются частично

`app.js:459–472`: план увеличивается отдельно от списания накоплений/резерва. При отказе второго запроса план уже изменён, источник не уменьшен; повторное покрытие может быть недоступно, поскольку план сравнялся с фактом.
`index.html:370–387`: перенос создаёт назначение отдельно от удаления источника; отказ удаления оставляет дубликат, повтор добавляет ещё один.
`index.html:343–358`: создание периода и копирование строк разделены; отказ копирования оставляет созданный пустой период.

Исправление: транзакционные серверные операции с проверкой доступа и защитой от повторного выполнения. Готовность: отказ любого шага не оставляет частичный результат; повтор запроса не дублирует данные. Вывод подтверждён порядком запросов в коде, без fault injection в реальную БД.

### D05 · P1 · Две вкладки теряют независимые правки

`shared/core.js:166–172,335–343`, `free/index.html:617–620`: сохранение отправляет сразу несколько полей, а перечитывание другой вкладки откладывается при вводе. Воспроизведение: обе вкладки открыли доход 1000 и накопления 100; A меняет доход на 2000, B накопления на 300. Итог 1000/300 вместо 2000/300. Аналогичная проблема есть у полей строки; облачные обработчики также отправляют полные patch нескольких полей.

Исправление: отправлять только реально изменённые поля; для конфликтов одного поля использовать revision и понятное разрешение конфликта. Готовность: параллельные независимые правки сохраняются обе, конфликт одного поля не скрывается.

### D06 · P1 · Прибавление расхода не атомарно

`app.js:355–367,503–513`: ввод `+50` и быстрый расход вычисляют абсолютный итог на клиенте. При исходных 100 два устройства с прибавлениями 50 и 70 записывают 150 и 170; последнее значение заменяет первое, вместо ожидаемых 220. Realtime не сериализует эти операции.

Исправление: атомарное серверное прибавление с идентификатором операции либо контроль версии и повтор вычисления. Готовность: оба расхода учтены ровно один раз при конкуренции и повторе запроса.

### D07 · P1 · Автокопия может стать старее данных

`free/index.html:847,892–909`: очередь `fileWritePromise` работает внутри одной вкладки. Две вкладки используют общий сохранённый fileHandle. Позднее завершение записи старого snapshot может заменить уже записанный новый файл. В модели двух VM-контекстов итоговый файл содержал версию 1 после сохранения версии 2.

Исправление: межвкладочная блокировка всей операции «снять snapshot → записать → подтвердить», проверка версии, обработка отказа блокировки. Готовность: реальный браузерный тест с двумя вкладками и задержанным writer; файл содержит последний согласованный snapshot. В этом аудите реальная гонка двух системных file writers не проверялась.

### D08 · P2 · `/free/` выбирает другой период 1–9 числа

`shared/core.js:18–22`: 5 декабря выбирается декабрь, половина 2; по правилу выплаты из README нужен ноябрь, половина 2. Облачная версия делает поправку в `app.js:29–32`, локальная нет. VM с фиксированной датой подтвердил различие. Справка локальной версии описывает текущий месяц, поэтому конфликтует с общим правилом продукта.

Исправление: единая функция определения периода, одинаковые даты в интерфейсе и справке. Готовность: границы 1/9/10/24/25 и переход декабря/января проверяются в обоих режимах.

### D09 · P2 · Собственная копия может не пройти импорт

`shared/core.js:43,166–172`, `free/index.html:731–735`: ввод допускает `1e20`, IndexedDB сохраняет его; импорт отвергает модуль суммы больше `Number.MAX_SAFE_INTEGER / 100`. Получается файл, который само приложение не восстановит. Несовместимость валидаторов воспроизведена локально.

Исправление: единый контракт денег при вводе, записи и импорте, видимая ошибка вместо сохранения неподдерживаемого числа. Готовность: любое состояние, допустимое через UI, проходит export/import без изменения суммы.

### D10 · P1 · Отказ CDN оставляет пустой экран

`index.html:299,311`: загрузка Supabase SDK с внешнего CDN обязательна; оба основных контейнера изначально скрыты. В Chromium заблокирован HTTPS CDN: `Cannot read properties of undefined (reading 'createClient')`, видимый текст страницы пустой.

Исправление: поставлять закреплённый SDK вместе с приложением, показывать состояние загрузки и устойчивый экран ошибки с повтором. Готовность: отказ SDK, Auth и первичной загрузки данных не оставляет пустой экран и не выглядит как пустой бюджет. В аудитe непосредственно воспроизведён отказ SDK.

| Область | Результат и требование |
|---|---|
| Схема БД | SQL меняет существующие таблицы, не создаёт полную схему. Нужны миграции с нуля, ограничения, индексы и проверка обновления существующей БД |
| Разделение сред | В `index.html:309–310` фиксирован production endpoint. Нужен воспроизводимый тестовый контур; открывать корень локально без изоляции запросов опасно для проверки изменений |
| Автоматизация | В tracked файлах нет CI. 18 тестов проходят, но преимущественно используют VM/mocks и не доказывают корректность реальной БД, RLS и системных диалогов |
| Регрессии | Добавить проверки D02–D09, браузерные CRUD/export/restore/offline, контракт обоих адаптеров и отказов записи. Общий код и его переопределения в `app.js` проверять совместно |
| Cloud backup/recovery | Экспорт и восстановление через UI есть только в `/free/`. Настройки резервирования Supabase и фактическое восстановление не проверены; требуется отдельный restore drill |
| Наблюдаемость | Ошибка преимущественно показывается временным `flash`; нет доказанного процесса обнаружения сбоев и восстановления. Нужны устойчивый индикатор несохранённых изменений и процедура диагностики без финансовых данных |
| Обновления PWA | Базовый offline локальной версии проверен. Старый/новый код, IndexedDB migrations, обновление установленной PWA и плохая сеть на телефонах остаются release gate |
| Производительность | Малый тестовый бюджет работал. Большой архив, тысячи строк, холодный запуск и медленное устройство не измерялись; заявления о производительности не делаются |
| Безопасность | RLS рассмотрена по SQL; SDK закреплён версией. Аудит истории Git на секреты, фактических заголовков хостинга, настроек Auth, зависимостей на актуальные CVE и penetration test не выполнялись |
| Поддержка | У `/free/` есть версия, справка и предупреждение о публичности GitHub Issues. Для облака нужны явные версия, канал поддержки и сценарий восстановления доступа; в login нет действия «Забыли пароль» |

Это пробелы доказательств готовности, а не утверждение, что соответствующая инфраструктура отсутствует вне репозитория.

## UX/UI: приоритетные изменения

### U01 · P1 · Действия облачной версии недоступны с клавиатуры

`app.js:119–123,307–324,541–550`: категории и кнопки переноса/удаления имеют `tabindex="-1"`; альтернативы скрыты до свайпа. Покрытие перерасхода вызывается кликом по `div.rem`, у которого нет роли кнопки и клавиатурного обработчика. В отрисованном DOM это подтверждено.

Исправление: обычные доступные кнопки, явное меню строки, управление Enter/Space; смена категории через подписанный selector. Готовность: все операции выполняются без мыши и свайпа.

### U02 · P1 · Облачные формы потеряли подписи и управление фокусом

`app.js:313–320`: у полей строк нет `label`/`aria-label`; несколько полей с placeholder `0` не различимы по назначению. `index.html:115,146,162`, `app.js:491`: собственные окна калькулятора, быстрого расхода и покрытия открываются вне общего modal helper. Для быстрого расхода Chromium подтвердил отсутствие `role=dialog` и `inert` у фона. Общий helper в `shared/core.js:466` учитывает только confirm/settings.

Исправление: единый modal lifecycle, accessible name, фокус внутри окна и возврат к инициатору, подписи «План», «Факт» с контекстом строки. Готовность: Tab не уходит под диалог, Escape/закрытие возвращают фокус, screen reader различает поля.

### U03 · P1 · Недостаточный контраст рабочих элементов

Измерены используемые цвета, не субъективная оценка скриншота:

| Пара | Контраст | Где |
|---|---:|---|
| `#94a3b8` / белый | 2.56:1 | подписи, неактивные фильтры, «Добавить», shared/core.css:9,110,253–277 |
| `#10b981` / белый | 2.54:1 | положительный остаток и текст категории |
| `#ef4444` / белый | 3.76:1 | небольшой текст перерасхода |
| белый / `#3b82f6` | 3.68:1 | небольшие основные кнопки |

Для обычного текста требуется 4.5:1; для крупного текста применяется отдельный порог. Здесь замечание относится к небольшим подписям и кнопкам, не ко всем крупным суммам. Источник: [W3C, Contrast Minimum](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html).

Исправление: затемнить текстовые semantic colors и фон primary-кнопок, проверить все состояния на фактических поверхностях. Не заменять смысл только цветом.

### U04 · P2 · Основное действие ниже нескольких экранов

В первом запуске `/free/` при 390×844 верх кнопки «Создать бюджет» находился на y≈1132: раньше неё два информационных блока. В облачной версии перед добавлением расхода идут большая формула, два кошелька и обязательные платежи; быстрый расход расположен в конце секции трат. Это мешает частому действию «записать покупку».

Исправление: в первом запуске короткое объяснение и создание бюджета сразу; подробности в справке. В рабочем экране оставить главную сумму, сделать добавление расхода доступным без длинной прокрутки; формулу раскрывать по запросу. Проверить сценарий на новичках, не только экспертную оценку.

### U05 · P2 · Цветные категории скрывают смысл на телефоне

`shared/core.css:430,467`: selector превращается в круг 32×32 с `font-size:0`. На desktop видны «Я/Общие», на телефоне остаётся только цвет. В облаке круги тоже не показывают название без tooltip, недоступного обычному касанию.

Исправление: короткое название категории рядом с цветом, явный доступный выбор. Для удобства касания увеличить маленькие действия примерно до 44 px; это рекомендация удобства, а не заявление, что любой меньший элемент нарушает WCAG.

### U06 · P2 · Слишком мелкие подписи и слабые сигналы редактирования

В мобильной локальной версии подписи карточек 10 px, фильтры 12 px и высотой около 26 px; кнопки добавления серые с почти незаметной пунктирной границей. В облачной таблице поля выглядят как статические числа, а на телефоне в одной строке остаётся много столбцов. Снимки показывают сохранение структуры без горизонтального overflow, но это не равнозначно удобному чтению.

Исправление: рабочие подписи 12–14 px с достаточным контрастом, ясное состояние ввода, увеличение зон касания, для облачной мобильной строки разнести название и суммы на два ряда. Избегать принудительного одинакового веса у всех элементов.

### U07 · P2 · Термины и расчёты требуют знания авторской модели

`free/index.html:205–207`, `app.js:14–15,129–144`: «полумесяц», «спринт», «бэклог», «можно тратить», «остаток» и «свободно» обозначают разные вещи; лимиты 40000 и имя Насти закреплены в облачной модели. Это уместно для конкретной семьи, но не готовый публичный продукт.

Исправление: показывать точный диапазон дат в обеих версиях; «бэклог» пояснить как будущие покупки; рядом с главной суммой кратко объяснить, учитывает ли она планы. Для независимых семей настраивать участников, лимиты и дни выплат. Не добавлять настройки ради текущего личного режима.

### U08 · P2 · Обратная связь о сохранении исчезает слишком быстро

`shared/core.js:75–82`: успех виден 900 мс, ошибка 5 с; `#sync-dot` не имеет live region. После ошибки нет постоянного списка/маркировки неподтверждённых полей. На финансовом экране пользователь должен видеть, что изменение ещё не сохранено.

Исправление: состояния «Сохраняется / Сохранено / Не сохранено», ошибка рядом с полем и повтором, доступное объявление статуса. Данные не считать надёжно записанными по одному исчезнувшему toast.

### U09 · P3 · Лишняя кнопка перевода нулевой суммы

На облачном экране без плана Насти показано «Отметить: перевёл 0 ₽». Это не помогает следующему действию и отвлекает от трат. Скрыть или отключить с пояснением до положительной суммы; не менять модель перевода без отдельного решения.

## Визуальная оценка по семи направлениям

| Направление | Оценка |
|---|---|
| Иерархия | Главные суммы хорошо выделены; частые действия слишком далеко от начала экрана |
| Композиция | Карточки, интервалы и выравнивание дают понятные группы; мобильная облачная сводка чрезмерно длинная |
| Типографика | Числа читаются лучше подписей; мелкие подписи/инструкции и слабый контраст требуют исправления |
| Цвет | Палитра последовательна, но несколько рабочих сочетаний не проходят контраст; категории зависят от цвета |
| Affordance | У free понятнее подписи полей; у cloud скрытые свайпы, круги и кликабельный остаток требуют обнаружения |
| Плотность | Desktop упорядочен; onboarding и мобильная облачная сводка перегружены объяснениями до действия |
| Соответствие бренду | Не оценивалось: mood.md, voice.md и tokens.md в проекте не обнаружены; придуманные требования не применялись |

Сильная сторона: спокойная карточная структура и акцент на итогах. Слабая: доступность рабочих действий и путь до записи расхода. Полный редизайн не нужен для устранения этих проблем.

## Порядок подготовки релиза

1. **Целостность:** D02–D09 и тесты задержек/конкуренции/отказов. Для публичного облака одновременно D01 и миграции с нуля.
2. **Надёжный запуск:** D10, тестовая среда, CI, обработка несохранённых правок, проверенное восстановление БД/файлов и процедура отката.
3. **Основной UX:** U01–U03, затем U04–U08. Проверить задачу «создать бюджет → записать покупку → понять остаток → восстановить копию» без подсказок.
4. **Release gate:** реальные iPhone/Safari и Android/Chrome, установленная PWA, экранная клавиатура, offline, системный экспорт/restore, обновление со старой версии. Только после этого ограниченный пилот по `FREE_PILOT.md`.

Критерий готовности: нет открытых ошибок потери данных/неверного периода, все операции доступны, отказы понятны, восстановление доказано, платформенные проверки записаны. Зелёные текущие 18 тестов этих условий пока не обеспечивают.
