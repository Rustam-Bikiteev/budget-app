# Аудит и план выпуска Budget

Дата: 16.11.2026. Аудит исходников и документации, без изменения приложения или БД.

## Вывод

Есть основа узкого продукта: бюджет от выплаты до выплаты, план/факт, обязательные
платежи и список будущих покупок. Общая логика двух версий уже выделена.
Переписывать всё на другой framework ради запуска не требуется.

`/free/` подходит как основа ограниченной публичной беты после исправлений сохранения
и проверки восстановления. Облачный режим пока рассчитан на одну семью.
Открывать регистрацию независимых пользователей с текущими политиками нельзя.
Фактические политики, регистрация, резервирование и ограничения боевого проекта
Supabase не проверены: вывод о доступе относится к SQL в репозитории.

## Рекомендуемый путь к пользователям

### 1. Бесплатная бета на одном устройстве

Сначала довести `/free/`: исправить сохранение, объяснить периоды и отсутствие
синхронизации, добавить короткий первый запуск и инструкцию установки PWA.
Дать понятный канал поддержки и видимую версию приложения.

Проверить на реальных Safari iOS, Chrome Android и desktop Chrome/Edge/Firefox:
создание периода, ввод сумм, переносы, удаление категории, импорт/экспорт,
отмена восстановления, закрытие и повторное открытие, офлайн после первой загрузки.
Отдельно проверить потерю сети, отказ хранения и переполнение квоты.
Проверить клавиатурную навигацию, подписи полей и управление фокусом модальных окон.

Критерий: пользователь без объяснений создаёт бюджет и внешнюю копию, затем
восстанавливает её в чистом профиле браузера с теми же суммами и категориями.

Пригласить небольшую группу, например 10–20 человек, на несколько выплат.
Это рекомендуемый эксперимент, не оценка существующей аудитории.
Выяснить, понятна ли модель полумесяцев и возвращаются ли люди в следующий период.
Не отправлять в аналитику названия трат, суммы и содержимое копий.

### 2. Облачный продукт для нескольких семей

Минимальная целевая модель:

```
Supabase Auth user → budget_members(user_id, budget_id, role)
                  → budgets
                  → months / entries / backlog с привязкой к budget_id
```

Категории хранить в бюджете, а не зашивать имена в JS. Период уникален внутри
бюджета, не всей базы. Ограничения БД должны запрещать строке ссылаться на период
другого бюджета; одной фильтрации UI недостаточно.
RLS проверяет членство и роль для чтения, добавления, изменения и удаления.
Членство нельзя позволять создавать себе в чужом бюджете прямым API-запросом.

Нужны отдельные аккаунты, подтверждение email, восстановление пароля, приглашение
партнёра, отзыв доступа, выход с устройства, экспорт и удаление аккаунта/бюджета.
Семейный пароль не масштабируется на публичный продукт.
Миграция текущих личных данных требует резервной копии, тестового прогона и отката.

Для денежных значений выбрать единую точную модель: целые копейки с ограничением
диапазона либо согласованный decimal-подход. Проверять допустимые значения на
клиенте и в БД; явно решить, допускаются ли возвраты и отрицательные суммы.

Не добавлять двусторонний offline sync в тот же первый релиз: очередь изменений,
конфликты и миграция между режимами существенно расширят задачу. Локальная версия
может оставаться офлайн, облачная явно требовать сеть.

### 3. Платная версия

Гипотеза ценности: бесплатный личный бюджет, платные совместный доступ,
синхронизация между устройствами и управляемые облачные копии.
Сначала проверить готовность платить интервью и пилотом. Цены и спрос этим
аудитом не исследованы; делать вывод о выручке пока не из чего.

До оплаты нужны серверная проверка статуса подписки/покупки, проверка подписи
платёжных webhook, идемпотентная обработка повторных событий, возвраты и понятное
поведение после окончания доступа. Ключи оплаты не хранятся во frontend.
Платёжный сервис и применимые требования выбираются после определения страны
продавца, рынка и формы бизнеса. Юридическое заключение здесь не даётся.

Нужно подготовить пользовательские условия, описание обработки данных и поддержки;
проверить применимые требования к персональным данным, платежам и документам
продажи для выбранного рынка. Не обещать, что облако «не собирает данные».
Даже локальный режим не исключает обработку сетевых метаданных хостингом.

## Если речь о продаже самого приложения

Продажа доступа пользователям и продажа проекта покупателю требуют разной подготовки.
Для передачи бизнеса дополнительно нужны:

- Подтверждённые права на код, иконки, название и сторонние компоненты.
- Явная лицензия/условия использования кода. Публичный GitHub не определяет их вместо автора.
- Отдельные от личных аккаунтов домен, инфраструктура и платёжные настройки.
- Воспроизводимое развёртывание, миграции, восстановление backup и инструкция передачи.
- Подтверждённые показатели удержания, активных и платящих пользователей, расходов и дохода.
- Процедура передачи с заменой секретов и без включения личного бюджета автора в демонстрационные данные.

## Эксплуатационный минимум

Отдельные dev/staging/prod; статический frontend на подходящем хостинге; Supabase
можно сохранить. Vite/ES modules полезны при росте кода, React и собственный сервер
для всего приложения не являются обязательным условием выпуска.

Настроить backup БД с регулярной проверкой восстановления, мониторинг доступности
и ошибок без финансовых payload, журнал миграций, процедуру отката frontend и БД.
Зависимости закрепить и обновлять осознанно; для CDN продумать integrity или локальную
поставку. Настроить подходящие HTTP security headers и CSP; inline-обработчики
нужно учитывать при переходе на строгую CSP.
Оценивать расходы по фактическим активным пользователям, объёму хранения и Realtime,
не обещать бесплатную инфраструктуру без ограничений.

## Что проверено в этом аудите

- Прочитаны обе реализации хранилища, общие расчёты, backup/restore, service worker,
  манифесты, RLS SQL, README и локальный контекст проекта.
- Node.js: синтаксис inline JS обеих HTML-страниц, `shared/core.js`, `free/sw.js` корректен.
- Оба манифеста разбираются как JSON.
- Изолированно воспроизведён сбой `saveMonthFields`: после ошибки записи повтор
  тех же значений не вызывает API второй раз. Это проверка реального общего кода
  с подставленным отказом хранилища, не тест боевой базы.
- При исходном аудите UI в браузерах/на телефонах, реальный IndexedDB round-trip, offline/update,
  фактическая конфигурация Supabase, платежи и права на assets не проверены.

## Источники для решений

- [Supabase: Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security):
  разграничение строк по текущему пользователю и политикам; текущий `using (true)`
  не изолирует бюджеты.
- [GitHub Pages: limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits):
  Pages не предназначен и не разрешён как бесплатный хостинг коммерческого SaaS.
- [MDN: StorageManager.persist](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist):
  запрос persistent storage может вернуть false.

Ближайший практический шаг: надёжная локальная бета и проверка спроса; затем
изоляция семей и облачный пилот; после этого подключение оплаты.
